# UI/パフォーマンス設計ガイド

## モーダル表示の基本方針
- モーダルはクリック直後に必ず開く。
- モーダル表示のためにDB再取得を待たない。
- 追加データが必要な場合は「開いた後」にローディングを表示し、非同期で更新する。

### 詳細モーダルの未保存判定方針
- 保存必要有無の判定は `isDirty` ではなく差分計算で行う
- モーダル `open` 時点のスナップショット（元データ）を保持する
- `close` / `保存` / `変更を破棄` の各操作時に、現在値を取得して元データとの差分を再計算する
- `isDirty` は UI 表示専用の状態として扱う（保存判定ロジックには使わない）
- 詳細モーダルでは `isDirty=false` のとき主ボタン文言を「閉じる」、`isDirty=true` のとき「変更を保存」にする
- 詳細モーダルでは `isDirty=false` のとき「変更を破棄」ボタンを表示しない

## 実装ルール
1. 初期描画は `App.state.data` を使う。
2. 最新化が必要な場合はバックグラウンド更新を行う。
3. 再同期失敗時でもモーダルを閉じない。
4. 保存処理後の全体再読込は同期で待たず、背景で実行する。

## 非同期UIと保存確定の運用メモ
- create系モーダルは「即時クローズ + 楽観反映 + 背景同期」を基本にする。
- 一時的なレコードIDで先に一覧へ反映し、DB応答後に実IDへ置換または再同期で整合させる。
- 詳細モーダル内の編集操作（コメントを除く）はローカル状態で保持し、「変更を保存」押下時にまとめてDBへ反映する。
- 削除を詳細モーダル内で扱う場合も、即時DB反映ではなく「削除予約 → 保存時確定」を優先する。
- 参考実装は `task-detail` の dirty管理・保存導線を比較して設計する。

## Beer CSS利用ルール
- レイアウトは `row`, `grid`, `field`, `button` などの既存クラスを優先する。
- 一覧項目は `row middle-align` で縦崩れを防ぐ。
- カード内で情報を詰め込みすぎず、操作ボタン群を右側に分離する。

## Tabulator利用ルール
- 初期表示を最優先し、重い整形はホスト側で済ませてから渡す。
- iframe通信はトークン検証付き `postMessage` を維持する。
- クリック操作で再描画が必要な場合でも、全面ローディングではなく対象エリアのみ更新する。
